اگر من **کارفرما / Senior Backend Engineer** یک تیم نرم‌افزاری بودم، پروژه را به تو این‌طور تحویل می‌دادم؛ بدون اینکه بگویم دقیقاً چه مدل‌هایی بسازی یا کد را چطور پیاده‌سازی کنی:

# پروژه: Marketplace E-commerce API

## معرفی پروژه

ما قصد داریم یک **پلتفرم فروشگاهی/Marketplace** طراحی و پیاده‌سازی کنیم که در آن کاربران بتوانند محصولات را مشاهده و جست‌وجو کنند، محصولات را به سبد خرید اضافه کنند و سفارش ثبت کنند.

سیستم باید از ابتدا با دید یک محصول واقعی طراحی شود؛ بنابراین صرفاً یک CRUD ساده برای محصولات قابل قبول نیست.

Backend پروژه باید به‌صورت یک **RESTful API** مستقل پیاده‌سازی شود و هیچ وابستگی‌ای به Frontend نداشته باشد.

---

## کاربران و حساب کاربری

سیستم باید امکان ثبت‌نام و ورود کاربران را فراهم کند.

کاربران باید بتوانند اطلاعات حساب خود را مدیریت کنند و سیستم باید بتواند نقش‌ها و سطح دسترسی‌های مختلف کاربران را مدیریت کند.

حداقل دو نوع کاربر در سیستم وجود خواهد داشت:

* Customer
* Administrator

دسترسی هر بخش از سیستم باید بر اساس نقش و مجوز کاربر کنترل شود.

---

## کاتالوگ محصولات

سیستم باید یک کاتالوگ محصولات داشته باشد.

هر محصول می‌تواند دارای اطلاعاتی مانند:

* نام
* توضیحات
* قیمت
* وضعیت موجودی
* دسته‌بندی
* تصاویر
* وضعیت فعال/غیرفعال بودن

باشد.

مدیر سیستم باید بتواند محصولات و دسته‌بندی‌ها را مدیریت کند.

کاربر باید بتواند محصولات را مشاهده، جست‌وجو و بر اساس معیارهای مختلف فیلتر کند.

---

## سبد خرید

هر کاربر باید بتواند سبد خرید خودش را داشته باشد.

کاربر باید بتواند:

* محصولی را به سبد اضافه کند
* تعداد محصول را تغییر دهد
* محصول را حذف کند
* محتوای فعلی سبد را مشاهده کند

سیستم باید هنگام تغییر سبد، قوانین مربوط به موجودی و قیمت را در نظر بگیرد.

---

## سفارش‌ها

کاربر باید بتواند سبد خرید خود را به سفارش تبدیل کند.

سیستم باید چرخه عمر سفارش را مدیریت کند.

برای مثال سفارش می‌تواند وضعیت‌هایی مانند:

`Pending → Paid → Processing → Shipped → Delivered`

داشته باشد.

همچنین باید وضعیت‌های ناموفق مانند لغو شدن سفارش یا شکست پرداخت نیز در نظر گرفته شوند.

تاریخچه تغییر وضعیت سفارش باید قابل پیگیری باشد.

---

## پرداخت

سیستم باید برای پرداخت آنلاین آماده باشد.

در فاز اول می‌توان از یک Payment Gateway فرضی یا Mock استفاده کرد، اما معماری باید به شکلی باشد که در آینده بتوان Gateway واقعی را بدون بازنویسی بخش بزرگی از سیستم اضافه کرد.

پرداخت موفق نباید صرفاً بر اساس درخواست کاربر معتبر تلقی شود و سیستم باید بتواند وضعیت پرداخت را به شکل قابل اعتماد مدیریت کند.

---

## موجودی محصولات

موجودی کالا باید مدیریت شود.

سیستم نباید اجازه دهد تعداد بیشتری از موجودی واقعی سفارش داده شود.

همچنین باید مسئله همزمانی درخواست‌ها در زمان خرید یک محصول محدود نیز در نظر گرفته شود.

---

## جست‌وجو و فیلتر

API محصولات باید امکان جست‌وجو و فیلتر مناسب را ارائه دهد.

کاربر باید بتواند محصول موردنظر خود را بر اساس معیارهایی مانند دسته‌بندی، قیمت و وضعیت موجودی پیدا کند.

Pagination نیز باید برای endpointهایی که ممکن است حجم زیادی از داده برگردانند وجود داشته باشد.

---

## سیستم Cache

برخی داده‌های پرتکرار، خصوصاً داده‌هایی که تغییرات آن‌ها کم است، باید قابلیت Cache شدن داشته باشند.

هدف این است که در workload بالا، تمام درخواست‌ها مستقیماً به Database وابسته نباشند.

Cache باید دارای استراتژی مناسب برای invalidation باشد.

---

## پردازش‌های پس‌زمینه

برخی عملیات نباید باعث شوند درخواست HTTP کاربر تا پایان پردازش منتظر بماند.

برای چنین عملیات‌هایی باید از background task / task queue استفاده شود.

برای مثال:

* ارسال ایمیل تأیید سفارش
* ارسال notification
* پردازش برخی عملیات مربوط به سفارش
* عملیات دوره‌ای سیستم

باید قابلیت اجرا به‌صورت asynchronous/background را داشته باشند.

---

## Notification

سیستم باید بتواند در رخدادهای مهم به کاربر اطلاع‌رسانی کند.

برای مثال:

* ثبت موفق سفارش
* موفقیت پرداخت
* تغییر وضعیت سفارش
* ارسال سفارش

معماری Notification باید طوری باشد که اضافه کردن کانال‌های جدید در آینده امکان‌پذیر باشد.

---

## مدیریت خطا

API باید رفتار مشخص و قابل پیش‌بینی در برابر خطاها داشته باشد.

خطاهای validation، authentication، authorization، resource not found، business logic و خطاهای داخلی باید به شکل مناسب مدیریت شوند.

نباید جزئیات داخلی سیستم یا exceptionهای خام به Client نمایش داده شوند.

---

## امنیت

سیستم باید در برابر مشکلات رایج API و Web Application ایمن باشد.

حداقل موارد زیر باید در طراحی در نظر گرفته شوند:

* Authentication
* Authorization
* Password security
* Permission management
* Input validation
* جلوگیری از دسترسی غیرمجاز به منابع
* Rate limiting در بخش‌های حساس
* مدیریت امن اطلاعات حساس

---

## Database

اطلاعات اصلی سیستم باید در یک relational database ذخیره شوند.

ساختار Database باید برای رشد سیستم قابل توسعه باشد و روابط بین موجودیت‌ها به شکل صحیح طراحی شوند.

همچنین باید migration mechanism مشخصی برای تغییر Schema در طول توسعه وجود داشته باشد.

---

## API Design

تمام قابلیت‌های سیستم باید از طریق API در اختیار Client قرار بگیرند.

API باید:

* RESTful باشد
* ساختار URL مناسبی داشته باشد
* HTTP Status Codeهای صحیح برگرداند
* Validation مناسب داشته باشد
* Pagination داشته باشد
* Authentication و Permission داشته باشد
* Response structure مشخص و قابل پیش‌بینی داشته باشد

API باید طوری طراحی شود که یک Frontend مستقل بتواند بدون نیاز به دانستن جزئیات Backend از آن استفاده کند.

برای بخش‌های مهم سیستم باید تست خودکار نوشته شود.

حداقل باید سناریوهای زیر پوشش داده شوند:

## Containerization

توسعه‌دهنده باید بتواند پروژه و سرویس‌های موردنیاز آن را با یک فرآیند مشخص اجرا کند.

سرویس‌های وابسته مانند Database، Cache و Task Worker نیز باید در محیط development قابل اجرا باشند.

* نصب dependencyها
* اجرای testها
* بررسی خطاهای پروژه

به‌صورت خودکار انجام شوند.

ساختار پروژه باید قابلیت توسعه به سمت deployment خودکار را نیز داشته باشد.

## Logging و Monitoring

سیستم باید Log مناسب تولید کند.

Logging نباید شامل اطلاعات حساس کاربران یا credentialها باشد.

همچنین ساختار پروژه باید برای اضافه کردن monitoring و observability در آینده مناسب باشد.

## معیار پذیرش پروژه

پروژه زمانی قابل قبول است که:

1. تمام قابلیت‌های اصلی از طریق API قابل استفاده باشند.
2. کاربران فقط به منابع مجاز خود دسترسی داشته باشند.
3. ثبت سفارش و مدیریت موجودی رفتار قابل اعتماد داشته باشد.
4. سیستم در برابر درخواست‌های همزمان رفتار صحیحی داشته باشد.
5. عملیات‌های سنگین از چرخه request/response خارج شده باشند.
6. Cache برای workloadهای مناسب استفاده شده باشد.
7. تست خودکار بخش‌های مهم را پوشش دهد.
8. کل پروژه به‌صورت reproducible اجرا شود.
9. CI بتواند صحت تغییرات را بررسی کند.
10. پروژه مستند باشد.
11. ساختار کد و معماری به شکلی باشد که بتوان قابلیت‌های آینده را بدون بازنویسی اساسی سیستم اضافه کرد.
